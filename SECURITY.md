# Security policy

## Supported versions

| Version | Supported |
| --- | --- |
| 1.0.x | yes |
| < 1.0 | no |

Only the latest release is supported.
This is a single-maintainer hobby project, so there is no backporting: a fix lands on `main` and goes out in the next release.

## Reporting a vulnerability

Please report privately rather than in a public issue.

Use GitHub's private vulnerability reporting: the **Security** tab of this repository, then **Report a vulnerability**.
That opens a draft advisory only you and the maintainer can read, and it needs no email address from either of us.

Please include what the bug lets an attacker do, which version and platform you saw it on, and the smallest reproduction you have.

## What to expect

No service level agreement is offered, because none would be honest.
This is somebody's spare-time project, not a product with an on-call rota.

In practice: an acknowledgement within about a week, and a fix for anything that reaches the mesh keys as quickly as a fix can be written and tested.
If a week passes with no reply, assume it was missed rather than ignored, and nudge the report.

Once a fix is released the advisory is published with credit, unless you ask otherwise.

## Please do not send your mesh export

The `.connect` file the Häfele Connect app exports contains the network key and the application key of your mesh.
Between them those two are full control of your lights: anyone holding them can turn them on, change them, and keep doing so for as long as the keys are in use.
They are not a configuration detail that happens to be sensitive, they are the credential itself.

So do not attach your own export to a report, do not paste it into an advisory, and do not put it in an issue.
If a reproduction needs a mesh document, use `tests/fixtures/sample.connect`, which is generated by `tests/make_fixture.py` and is entirely fictional.

The same goes for the bridge's log and for `state.json`: check them before pasting, and replace anything you are not sure about.

## Scope

In scope: anything that discloses the mesh keys, lets an unauthorised party send commands into the mesh, or lets data arriving from the MQTT broker or the mesh take control of the bridge process.

Out of scope, because they are documented decisions rather than bugs:

- The container runs as root and is given the host's D-Bus socket, which BlueZ requires.
  A host you do not trust is a host that already has your keys; see the README's deliberate omissions.
- The bridge trusts whoever can publish to its MQTT topics.
  Authorisation belongs to the broker, and the bridge is configured with a username and password for exactly that reason.
- Bluetooth Mesh itself is as secure as its keys, which are shared with every node in the network by design.

If you are unsure which side of that line something falls on, report it anyway.
