# Changelog

All notable changes to hafele2mqtt are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [semantic versioning](https://semver.org/spec/v2.0.0.html).

`__version__` in `app/__init__.py` is the single place the version is written. The bridge reports it to Home Assistant as `sw_version`, prints it at start-up and on `--version`, and `scripts/deploy.sh` reads it from there.

## [1.0.0] - 2026-11-19

First release: everything below is what the bridge does, rather than a record of how it got there.

### Added

- **A Häfele Connect Mesh bridge that needs no gateway.** It speaks BLE Mesh over a GATT proxy node, so the only hardware involved is the Bluetooth adapter already in the machine running it and a Häfele box in range.
- **Your own `.connect` export is the configuration.** The file the Connect app writes carries the network key, the application key, the node list, the groups and the scenes, so there is nothing to pair, commission or type in by hand.
- **Home Assistant MQTT discovery** for lights, groups and scenes. Every entity has a stable `unique_id`, so renames in the UI, dashboards and automations survive a re-export of the mesh file.
- **Connect groups arrive as `light.*` entities**, which means the groups made in the Häfele app keep working as they are instead of having to be rebuilt as Home Assistant light groups. Scenes arrive as `scene.*`.
- **Entities keep their identity when the mesh moves underneath them.** A `unique_id` is minted from the mesh address, which is the one thing in a Connect network that is not stable: re-provisioning a box or rebuilding a group hands out new addresses. So the bridge records the GUID each entity is anchored on against the id it was published under, persists that in the state file, and re-applies it on every start. A known device on a new address keeps its entity; a new device moving onto a freed address cannot take it over; an export that gives two devices one GUID is refused rather than guessed at.
- **Each light belongs to a device representing its physical box**, carrying the box's model, hardware revision and firmware, with the bridge as `via_device`. Groups belong to the bridge device, scenes to a device of their own reached through it, and a box suggests an area when every light on it agrees on the same Connect room.
- **An optional `entities.yaml`** to pin a name against renames in the Connect app, ask for a readable `entity_id`, set an icon or an area, pin a `unique_id` when migrating off another bridge, or hide an entity entirely. Opt-in in both directions: with no file present, nothing in it runs and nothing it could change is changed. The README is explicit about the two things Home Assistant will not do, namely rename an entity or move a device that already exists.
- **Availability follows the mesh, not the broker.** Lights and scenes require two things at once: the bridge process is alive (the MQTT last will) and the BLE proxy link is up. A dead link shows up as unavailable entities rather than a stale state that quietly lies. The two are separate topics because the diagnostics hang off the first one only: an entity that goes unavailable at the exact moment it has something to report would be worse than none.
- **The bridge picks the radio that can actually hear the network.** Two Bluetooth adapters in one machine do not hear the same things, and a radio that is deaf to the mesh looks identical to a mesh that is switched off. So when no adapter is pinned, or the pinned one is not there, the bridge enumerates every adapter over BlueZ, scans with each, and keeps whichever sees the Mesh Proxy advertisement for *our* network, loudest first, logging what each one heard. `BLE_ADAPTER` accepts the adapter's MAC address as well as `hciN`, which is the form worth using: `hciN` is a boot-order label, so a reboot or a re-plugged dongle can move it onto different hardware while the configuration still looks correct.
- **"Down" is three states, not one.** No adapter at all, an adapter that cannot hear this network, and a proxy that is visible but whose GATT link will not hold are different problems with different answers, so each is named in the log and exported to Home Assistant rather than all arriving as "connection failed".
- **A recovery ladder instead of retrying the same thing.** After three consecutive failures the bridge scans for longer, after six it power-cycles the adapter through BlueZ, after nine it re-checks every adapter and switches to one that hears the mesh. Cheapest first, one log line each saying why it is being attempted, and it stops at the top rather than cycling. It is reset by a link that held for a minute, not by a connection that merely opened, because a radio that connects and drops straight away would otherwise keep the count near zero and never climb the ladder at all.
- **Diagnostic entities on the bridge device**: the proxy link as a `connectivity` binary sensor, the state in words, the adapter in use, the last signal strength, the number of drops since start-up and when the last one was. They read one retained JSON document, so the whole picture is written in a single publish and cannot be read half-updated.
- **Reconnecting to the broker re-sends what the bridge last knew.** State is published only when it changes, so a publish that happens while the broker is unreachable is not retried, it is lost, and the retained value then stays wrong until that same light next changes by itself. Re-publishing on connect turns that from permanent into a gap of seconds; entities the bridge has never heard a real value for are left alone rather than invented.
- **Optional MQTT over TLS**, off by default so that a plaintext broker on the same LAN keeps working untouched. `MQTT_TLS_CA` names a private CA, or is left empty for the system trust store, and `MQTT_TLS_INSECURE` drops the hostname check for a certificate issued under a name the bridge cannot use, which the README is blunt about: it keeps signature verification but gives up telling your broker apart from anything else holding that certificate. The start-up probe and the long-lived client are configured identically, so the probe can never pass on a connection the bridge then fails to make, and the two symmetrical mistakes that both present as a hang - TLS pointed at a plain listener, plain MQTT pointed at a TLS one - each exit with a line naming `MQTT_TLS` rather than the port.
- **A start-up poll that waits for the radio and chases what stays quiet.** A restarted bridge knows nothing, and it refuses to publish a state it has not been told, so until a node answers its entity has no state at all. Mesh status messages are unacknowledged, which means a request lost on air is lost in silence. So the first poll waits for the proxy link rather than being skipped while the radio is still scanning, every status request goes out as many times as a command does, and whatever has still not answered is asked again on a widening gap - only those, never a second full sweep, because reads are spent sequence numbers. Anything that never answers is named in the log with the number of attempts, rather than being left as a blank card in Home Assistant with no explanation anywhere.
- **Correct mesh crypto state across restarts.** The IV index and the outgoing sequence number are persisted and floored on start, so the bridge never replays a sequence number a node has already seen. While the network is mid-IV-update the bridge keeps transmitting on the index it has and accepts both, adopting the new one only once the update is over, because a value taken a year early could not be taken back.
- **A source address that moves itself before its counter runs out.** A mesh sequence number is 24 bits and spent rather than wrapped, so any one address has a finite life. With a million numbers left the bridge adopts another free unicast address, re-whitelists it on the proxy and carries on; the addresses it has used are never offered to it again. The specification's answer is an IV update, which belongs to the network's provisioner, and this bridge is a guest.
- **A message already heard is not heard again.** Mesh status messages are unauthenticated against replay by the transport itself: anyone within radio range can record one and send it back later, and without a check the bridge would publish that stale brightness as the light's current state. So the bridge keeps the newest `(IV index, sequence number)` it has accepted from each node and refuses anything that does not beat it, which also covers the ordinary case of a relayed message arriving twice. The table is kept only for addresses that appear in the mesh file, so nothing an outsider sends can make it grow, and it is held in memory rather than on disk: writing it durably would mean a flush per status message, against a worst case of one stale value that the next poll corrects.
- **The proxy says whether it took the filter, instead of the bridge assuming so.** The two configuration messages that ask a proxy to forward only what is addressed to this bridge go out as Write Without Response, so they are reported as sent the moment they leave the radio, whether or not the proxy agreed. A filter that was never applied looks exactly like a mesh where no light answers, with nothing in any log to tell the two apart. The bridge now reads the proxy's own Filter Status and logs which of the two happened, on every connection and on every address rotation. The waiting happens in the background: a rotation holds the send lock with a command queued behind it, and a log line is never worth delaying a light for.
- **A message the bridge cannot read is reported rather than dropped in silence.** Everything the bridge sends fits an unsegmented access message with room to spare, and building one that does not is refused at the source instead of being sent and discarded by every node without a word. The other direction is not the bridge's choice: a node that answers with a segmented message was previously dropped at the point the segmentation bit was noticed, so a light that reports its state in a way the bridge cannot reassemble was indistinguishable from a light that never answered. It is now named once per node, with the address, so the silence has an explanation.
- **Reassembly that cannot be made to misbehave from the air.** Every message on this link arrives in twenty-byte pieces, because the proxy connection's MTU is the smallest one Bluetooth defines and nearly nothing fits in it. The reassembly buffer is bounded, so a stream of beginnings from anyone in range cannot grow it without limit; it is cleared when the link drops and when a connection is made, so half a message cannot be completed by an unrelated one after a reconnect; the message type is taken from the first piece rather than the last, and pieces that disagree about it are discarded; and a continuation that belongs to no beginning is discarded rather than treated as one.
- **A network that never beacons is a warning, not a mystery.** The IV index is learned from authenticated network beacons, which is also the only way the bridge can catch up if the network's index moves while it is down. If no beacon arrives at all on a link that is up, nothing fails immediately and everything fails eventually, so the bridge counts them and says so once rather than leaving it to be deduced.
- **A transaction identifier per destination.** The specification identifies a transaction by source, destination and identifier together, so one counter for the whole bridge wraps against the wrong thing: enough commands to *any* lights in quick succession, rather than to one light, and a node treats a genuine new command as a repeat of the one before and ignores it. Each destination now counts its own.
- **A bound on what the broker can spend.** Commands arrive from a broker the bridge does not own and each one costs two sequence numbers, so a stuck automation can burn through unicast addresses without the lights showing anything. Incoming commands are held in a bounded queue at a configurable rate (`CMD_QUEUE_MAX`, `CMD_RATE_LIMIT`), with defaults far above normal use and a burst allowance of a full queue so a scene switching everything at once is not slowed. The part that actually saves the counter is coalescing: a second command for an entity that already has one waiting replaces it in place rather than queueing behind it, so a brightness slider drag becomes one command instead of dozens, and it keeps collapsing while the rate limit waits. A full queue drops its oldest entry, because being behind is when the newest instruction matters most, and throttling is reported once per ten seconds with counts rather than once per command.
- **`--validate`**, which loads and checks the mesh file and prints every entity and topic it would publish, with no Bluetooth and no broker involved. `--purge-discovery` retracts what a previous run published.
- **`--dump-overrides`**, which writes out a complete `entities.yaml` holding everything the bridge publishes right now, so that "what does the mesh look like today" is a file rather than a memory. Reading it back changes nothing, which is the one property that makes it worth anything: keep it in version control, run it again after the next export, and the diff is the list of what the Connect app moved. Deterministic by design, with no timestamp and no run id, and it works from the export and the state file alone, with the bridge down. Values it cannot set, such as mesh addresses, group membership and node UUIDs, are printed as comments rather than left out, because they are exactly what a re-export changes. Keeping the file is optional in every sense: identity across re-addressing lives in the state file either way. `entities.yaml.example` is the output for a made-up network.
- **One readable line for every foreseeable misconfiguration.** Checks run cheapest first (mesh file, state directory, MQTT, Bluetooth), and a bad setup exits immediately instead of looping in a reconnect at 3 a.m.
- **A container healthcheck that answers one question honestly.** The bridge touches a heartbeat file on every turn of its poll loop and the `HEALTHCHECK` reads its age, so unhealthy means the loop has stopped going round rather than "something, somewhere". It is deliberately not wired to the radio: a BLE reconnect is ordinary, restarting the container does not bring one back, and a warning that is usually on is a warning nobody reads. Mesh reachability stays on `hafele/status` where Home Assistant already reads it. The heartbeat is an inode timestamp on a tmpfs, so it writes no data and costs a Raspberry Pi's SD card nothing, and the staleness limit is derived from `POLL_INTERVAL` with `HEALTH_MAX_AGE` to override it.
- **A Docker image and a compose file**, plus `scripts/deploy.sh`, which builds this checkout, starts the service, asks the running container which version it actually is, and publishes that to Home Assistant as `sensor.hafele2mqtt_deployed_version`.
- **A test suite that needs neither Bluetooth nor a broker**, including the mesh crypto vectors and the discovery payloads, run against an anonymised `.connect` fixture.

### Note for anyone replacing an earlier private build

The bridge device is identified as `hafele2mqtt`. If an earlier build used a different identifier, Home Assistant will show a new bridge device and leave the old one behind, empty. The entities themselves are matched on `unique_id`, not on the device, so they move across keeping their entity ids: dashboards and automations are unaffected, and the old device can be deleted.
