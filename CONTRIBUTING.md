# Contributing

Thanks for looking.
This is a small single-maintainer project, so the bar is "does it work and can the next person read it", not a process.

## Running the tests

```sh
pip install -r requirements-dev.txt
python -m pytest
```

The suite needs no Bluetooth, no broker and no hardware, and it runs in a few seconds.
A change that cannot be tested without a radio is a change that wants rethinking, because almost everything here already is.

CI runs the same command, plus one extra check: `tests/fixtures/sample.connect` is regenerated by `tests/make_fixture.py` and the result must match what is committed.
If you touch the generator, regenerate the fixture in the same commit.

## Linting

There is no linter wired into CI, so there is no lint command to run.
That is a deliberate omission rather than an oversight: a linter added now would spend its first thousand findings on existing code and teach nobody anything.

What is expected instead:

- 100 columns, four spaces, type hints on anything public.
- Comments explain why, not what.
  The code already says what it does; a comment earns its place by recording the reason a decision went one way, so the next person does not undo it.
- `python -m pyflakes app tests` before you push is a cheap way to catch an unused import or a name that does not exist.
  It is not a dependency of the project; install it if you want it.

## Never commit a real mesh export

The `.connect` file the Häfele Connect app exports contains the network key and the application key of your mesh, which together are full control of your lights.
`.gitignore` already excludes `*.connect`, `config/` and `data/`, and nothing should be added that makes it easier to get one of them past that.

Use `tests/fixtures/sample.connect` in tests and in bug reports.
It is generated, obviously fake, and has neutral names.

If you believe you have found a security problem, read [SECURITY.md](SECURITY.md) before opening an issue.

## Dependencies are pinned

`requirements.txt` holds exact versions, and every action in `.github/workflows` is pinned to a commit SHA.
Both are there so that nothing upgrades without somebody deciding it should, which is also why `.github/dependabot.yml` exists: Dependabot is what proposes the upgrades, and a pull request is where the deciding happens.

If a change needs a new version, bump the pin in the same pull request and say what the new version is for.
Adding a new runtime dependency is a bigger conversation than it looks: the image is built for amd64 and arm64, and anything without wheels for both is a source build on a Raspberry Pi.

## Pull requests

One change per pull request, with the reasoning in the description rather than only in the diff.
Tests for anything a future refactor could quietly break.
If the change is user-visible, update the README and `CHANGELOG.md` in the same pull request.
